Overview

How staff get notified

There are two layers to this proof of concept: what the demo does today, and what a production version would do for the building.

What this demo does

When a resident submits a request, the app prepares a clear text message: the building, unit, category, urgency, description, request ID, and time. It also lists the staff roles who should be notified.

On a phone, a Send text button opens the device’s own Messages app with that note already filled in, using a standard sms: link. The resident (or a staff member helping them) taps Send. On a computer, the same message can be copied or opened on a phone by scanning a QR code. A Call button is available too, especially for emergencies, using a standard tel: link. Emergency requests also remind people to call 911 first if anyone is in danger.

If more than one person should be notified, iOS uses sms:/open?addresses=…&body=… and Android uses sms:number,number?body=…. When those people currently share the same number, the demo sends one text and lists every role in the message so no one is double-texted.

The page log records that a text was opened on the device. It does not send anything by itself. Phone numbers in the manager console are the numbers used in those text and call links — change a number, and the next message uses it.

What a production version would do

In a live building system, the resident would simply submit the request. A small backend would send the text (and, when needed, place a call) automatically from a dedicated building number, without using the resident’s personal messaging plan. If no one acknowledged the request in the time set by the routing rules, the next person would be notified automatically. Staff could reply or tap a link to acknowledge. Tenants would still use either the web portal or the app.

A practical setup is Twilio for SMS and voice, plus a hosted backend such as Supabase or Firebase (or a small Cloudflare Worker) to store requests, apply routing rules, and keep the tenant and manager views in sync across devices. US application-to-person texting also requires A2P 10DLC registration — a standard carrier process that identifies the building or management company as the sender.

Estimated cost for one building

Figures below use Twilio’s published US pricing as of November 2026 and assume modest volume for a single property. Carrier fees can add a fraction of a cent per text. Prices can change.

  • Local number: $1.15 per month
  • Outbound SMS: $0.0083 per 160-character segment, plus carrier pass-through fees (typically about $0.0025–$0.005)
  • Outbound voice: $0.014 per minute
  • A2P 10DLC, low-volume mixed use (a good fit for one building): about $4.50 brand registration and $15 campaign vetting, one time, then $1.50 per month. (Sole proprietor campaigns are $2/month; standard campaigns can be $10/month.)
  • Backend hosting: often $0 on a free tier for one building; a paid plan is typically $0–$25/month if you outgrow the free tier.

Typical monthly total for one building: about $5–$15 at a few hundred texts, once registration is complete. One-time A2P setup is about $20.

If you also want store apps

The tenant experience here is already an installable web app (a PWA) with its own home-screen icon. Shipping a true iOS or Android app could be done later with Capacitor or Expo, using the same design. Apple’s developer program is $99 per year; Google Play registration is $25, one time.
